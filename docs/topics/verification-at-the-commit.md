**Owner:** this repository.

**AES-INV-004 — a repository that declares how it is verified must run that
declaration on its own commit path.**

Verification an agent invokes by hand is advisory. The exit status of a check
can be discarded by how the command was composed, and there is no bound on the
ways to compose it wrongly, so there is no useful rule about the composition.
The check has to sit where the work becomes durable.

**Enforcement tier: enforced.** `scripts/check_verification_reaches_the_commit.py`
exits 1 and this invariant reports FAIL.

**It is failing right now against its declared consumer, and that failure is the
observation this invariant was created from.** See below.

**Why this exists.** On 2026-09-05, in the first governed consumer run this
system has ever had, the implementing agent verified its work with:

```
uv run python -m pytest -q 2>&1 | tail -2 && uv run ruff check . 2>&1 | tail -1 && git commit ...
```

The pipe into `tail` makes the pipeline's exit status `tail`'s, which is 0.
`pytest` printed `1 failed, 22 passed`. The `&&` chain continued anyway, `ruff`
printed `All checks passed!` on the next line, and a commit was created over a
red tree. The agent noticed later and repaired it inside the same pull request,
so nothing red reached `main`.

Nothing in the repository caught it. `whygame-reboot/CLAUDE.md` declares
`uv run python -m pytest -q` under its Verification heading, and no hook runs it.

**The wrong lesson and the right one.** The wrong lesson is "do not pipe into
`tail`". A rule against one status-discarding idiom leaves every other idiom
permitted — a swallowed subshell, a `;` where `&&` was meant, a wrapper that
returns 0 — and each would need its own rule, written after its own incident.
The right lesson is that a repository whose only protection is the care of
whoever last typed a command is not protected by its tests.

**Scale.** This is not local to one repository. The global pre-commit hook's own
header records that `install_governed_repo.py` maps `hooks/pre-push` and never
`hooks/pre-commit`, and that 105 repositories have no pre-commit hook at all.
The condition the checker names is the ecosystem's normal state.

**How the checker decides.** It reads the command lines a repository declares
under a checks-like heading in its own `CLAUDE.md`, derives from each the token
that names what is actually executed — a script path, a module after `-m`, the
target of a target-taking runner — and asks whether any of those reach the
`pre-commit` file on the path Git will really use, following the chain into the
repository's own `hooks/` directory.

Three outcomes. `PASS`, `FAIL`, and `NOT_CHECKED` for a repository that declares
no runnable check, which is unmeasured rather than passing and is reported at
least as loudly.

**Two things the checker got wrong before it was trusted**, both caught by
running it rather than reading it, and both recorded here because a control is
not evidence until it has been observed failing:

1. Its first version carried a fixed list of tool names (`pytest`, `ruff`, …).
   That list did not intersect what this repository declares about itself, so
   AES reported `NOT_CHECKED` — a selector matching nothing and calling it a
   clean sweep, which is the exact failure this repository has recorded three
   times. The vocabulary is now derived from each repository's own declarations.
2. Its second version also took the first bare word of every command segment.
   `git config core.hooksPath hooks` therefore contributed the token `git`,
   which appears in every hook ever written, and this repository passed its own
   check on a word that means nothing. Only tokens naming something executed
   count now. Under-matching produces a visible false `FAIL`; that false `PASS`
   was invisible.

**What it does not claim.** It does not check that the declared verification is
adequate, that it covers the change, or that it was passing — only that it is
reachable from the commit boundary at all. A repository can satisfy this and
still be badly tested. It cannot satisfy this and have a red tree commit
silently because of how a command was written.
